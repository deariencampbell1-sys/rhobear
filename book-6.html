LESSON 6.1

The assembly line for a mind.

"A trained model isn't grown. It's manufactured — six stations, in order, each one a thing you can point at."

Nobody "makes an AI" in one step. You take a model somebody else already spent millions training — the base — and you run it down a short assembly line that bends it toward your job and shrinks it to fit a laptop. Six stations. Miss the order and nothing works; know the order and the whole thing is legible.

Tap each station. This is the map for the entire book — every later lesson zooms into one of these boxes.

Interactive · The six stations
◇ Checkpoint 6.1
Why do we start from a base model instead of training from scratch?
Right. The base is a paid-for miracle. Training from scratch costs millions and needs oceans of data. Fine-tuning borrows all of that and adds only the last 1% — your flavor — for the price of a sandwich.
◈ Scar — a real one
The model we almost lost to a slow pipe.

We trained Forge, quantized it, and left the 4.7GB file sitting on the rented GPU box, planning to pull it "in a minute." The box throttled the download to a crawl, then the credits ran dry and it shut off — with the file still up there.

The lesson, now a law: the second an artifact exists, push it to a durable home you don't rent by the minute. Storage is cheap and permanent; compute is expensive and temporary. Never let the only copy live on the machine that's billing you.

LESSON 6.2

Choosing the raw material.

"Every base model is a trade. More brains, more drag. More reach, more weight. You pick the trade on purpose."

A base model has a few numbers that decide everything downstream. Parameters (the "7B" = 7 billion) are raw brain-cells: more means smarter but slower and heavier. Context is how much it can read at once — a normal model sees ~a few thousand words; a 1-million-token model can swallow a whole codebase. And the flavor it was pre-trained in matters: an -Instruct model already follows orders; a -Coder model already thinks in code.

For our two models we chose deliberately: Scribe (the writer) on Qwen2.5-7B-Instruct; Forge (the debugger) on Qwen2.5-7B-Instruct-1M — same size, but the 1M context so it can hold an entire repo in its head while it reasons. Flip each card for the why.

◇ Checkpoint 6.2
We wanted a debugger that could read a whole codebase at once. Which spec mattered most?
Context won. A bug that spans five files is invisible if the model can only see one. We traded nothing on size (still 7B) and bought a 1-million-token window — the debugger reads the whole scene, not a keyhole.
LESSON 6.3

Teaching by showing.

"You don't program the new skill. You show a thousand examples of it and let the weights soak it up."

Fine-tuning learns from examples, not rules — pairs of "here's the input, here's the ideal answer." But nobody sells a dataset of our exact harness and our exact voice. So we made one: we asked a strong teacher model (DeepSeek) to generate thousands of examples in the shape we wanted, then trained our small student on them. That's distillation — pouring a big model's skill into a small one.

For Forge the examples weren't "write this code." They were diagnose this bug, rank the causes, then question your own answer. 1,369 of them, across eight skills, deduped and shuffled. The self-doubt is trained in on purpose — a debugger that never second-guesses is a debugger that's confidently wrong.

Interactive · What one training example actually looks like
◇ Checkpoint 6.3
Why synthesize the dataset instead of downloading one?
Exactly. The moat is the specificity. A model that knows our deploy chain and questions itself can't be learned from the open internet — it has to be taught, example by example, in the shape only we know we need.
◈ Scar — a real one
The examples that ate their own quotes.

The teacher returned each batch as JSON. But the answers contained code — with ``` fences and quotes and newlines inside. Our parser split on the first ``` it saw, shredding the JSON, and whole batches came back empty. The flagship "diagnose" skill kept scoring zero and we couldn't see why.

The lesson: when your data contains the very characters your format uses as delimiters, the naive parser will betray you silently. We stopped splitting on fences and wrote a salvage reader that walks the text and rescues every complete object — even from a mangled batch. Data plumbing breaks quietly; verify counts, don't trust "it ran."

LESSON 6.4

Training on a budget: QLoRA.

"You don't rewrite the whole brain. You bolt on a tiny, cheap adapter — and freeze everything else."

Fully retraining 7 billion parameters needs enterprise GPUs and real money. LoRA is the trick that made this a hobby: freeze the giant base, and train only a pair of small "adapter" matrices — a fraction of a percent of the weights — that nudge the model's behavior. QLoRA adds one more squeeze: load the frozen base in 4-bit (quantized), so the whole thing fits on a single rented card. Q + LoRA = a 7B model trained on one 40GB GPU for a few dollars.

◇ Checkpoint 6.4
In QLoRA, what actually gets trained?
Just the adapter. The frozen base is the borrowed genius; the tiny trained adapter is the only thing that's "ours." That's why one cheap GPU and a few hundred examples is enough to move a 7B model.
◈ Scar — a real one
The night the toolchain ate the toolchain.

Halfway through, one install command quietly dragged in a newer PyTorch built for a GPU driver the box didn't have — so the GPU vanished (cuda: False) — and swapped a library to a version that broke a second library on import. Training died three different ways in a row, each error pointing at the wrong thing.

The lesson: your environment is a load-bearing wall. Pin exact versions, install them as one coherent set, and use --no-deps so a small package can't silently reach up and replace your big ones. Half of "the model won't train" is really "the plumbing changed under me."

LESSON 6.5

Shrinking without lobotomizing.

"A raw model is 15 gigs of high-precision numbers. Most of that precision is wasted. Quantizing throws it away — carefully."

Every weight in a fresh model is a fat 16-bit number. Quantization rounds them down to 4-bit — like saving a photo as a smaller JPEG. Done blindly it lobotomizes the model; done well (the Q4_K_M scheme keeps a little more precision on the weights that matter) it barely changes the answers while cutting the file to a third of the size. That's how a 15GB model becomes the 4.7GB file that runs on a laptop with no GPU.

Drag the dial. Watch size, quality, and speed trade against each other — and see why Q4_K_M is the spot almost everyone lands on.

◇ Checkpoint 6.5
Why not just quantize as hard as possible (Q2) to get the smallest file?
The knee of the curve. Quantization is a dial, not a switch. Too little and it won't fit the device; too much and you shipped a worse product. Q4_K_M is where size stops mattering and quality still holds.
◈ Scar — a real one
The merge that refused to convert.

To quantize, you first merge the trained adapter back into the base and save one clean model. We did — but because the base was loaded in 4-bit for training, the saved model still carried a "I'm quantized" tag in its config. The converter took one look and refused: Quant method not supported: 'bitsandbytes'.

The lesson: a 4-bit-trained model can't be exported directly. You reload the base clean in full precision, attach the adapter, merge that, and scrub the stale tag. One extra step — but skip it and the whole run is unshippable. We baked the fix into the script so it can never bite us again.

LESSON 6.6

Why it's fast — or slow — on a plain laptop.

"Everyone thinks a model is slow because of math. It's not. It's slow because of moving numbers."

Here's the thing almost nobody tells you: on a CPU, a language model isn't bottlenecked by calculation — it's bottlenecked by memory bandwidth. For every word it generates, it has to haul every weight from RAM into the processor. The math is trivial; the hauling is the whole cost. So the #1 lever for "low CPU drag" isn't a faster chip — it's a smaller model in memory. That's why quantization (Lesson 6.5) is a speed feature, not just a size one: half the bytes to move = roughly double the speed.

Three levers matter, in order: quantize (fewer bytes per weight), fewer active weights (the MoE trick, next lesson), and a short context (the "memory of the conversation," the KV-cache, grows with every word and has to be hauled too). Everything else is noise.

◇ Checkpoint 6.6
On a CPU, the biggest thing making a model slow is…
Bandwidth, every time. This is the secret that reframes everything: quantization and MoE aren't just about fitting on disk — they're about how few bytes cross the memory bus per word. Smaller footprint is the speed.
LESSON 6.7

MoE: a huge brain that only wakes a little.

"What if a 30-billion-param model only fired 3 billion per word? Big when it counts, cheap the rest of the time."

A normal ("dense") model lights up every weight for every word — all 7B fire, all the time. A Mixture of Experts splits the model into many small specialists and, for each word, a tiny router picks just the two or three most relevant ones to fire. So a "30B" MoE might only activate ~3B per word: you get the breadth of a huge model at the compute cost of a small one.

Two things people get wrong. First — you don't assign the experts by hand; which expert handles what emerges from training, and trying to author it is wasted effort. Second — MoE saves compute, not memory: all 30B still have to sit in RAM even though only 3B fire. That's why MoE is a dream on a server and a tight squeeze on a 16GB laptop — and exactly the tension you weigh when deciding what runs where.

◇ Checkpoint 6.7
An MoE with "30B total, 3B active" saves you on…
Compute, not memory. That one distinction decides where an MoE can live. On the server it's pure win. On a 16GB laptop the memory bill comes due — which is why the offline safety-net model stays a lean dense 7B.
LESSON 6.8

The tiered brain — and its one trap.

"Fast model scouts every problem. A slow, smart model only wakes for the hard ones. The whole bet lives in who decides 'hard.'"

Here's the frontier idea you sketched: run a fast scout on everything, and keep a heavy verifier asleep — waking it only when a cheap gate isn't sure the scout got it right. Easy questions stay fast and cheap; hard questions escalate to the big model. Adaptive compute: spend brains only where brains are needed.

But there's a knife-edge, and it is the whole product. Waking the verifier costs a full extra pass — checking is as expensive as answering. So the cascade only wins if the gate escalates rarely. Escalate too often and you've built something slower and more complex than just running the big model on everything. Drag the escalation rate and watch the bet flip from genius to worse-than-nothing.

◇ Checkpoint 6.8
What should the gate actually be trained to predict?
"Would tier-2 fix it?" Confidence lies — models are confidently wrong constantly. The gate's real job is to predict when the big model would overturn the small one. Train it on that, measure the real escalation rate, and only then trust the cascade. That one number decides if the whole design is worth building.

What you don't know yet.

◇ Checkpoint 6.9
We "vibe-checked" our models by reading a few answers. What does a real shop do instead?
Held-out evaluation. Reading a few answers proves it's not broken; it doesn't prove it's good. The grown-up move is a scored test set the model has never seen — the difference between "looks fine" and "we know." That's the first thing to add on your next run.
